# KT3 — Runtime & Hidden-Validation Readiness

Ветка: `fix/kt3-hidden-validation-runtime` (от `main` @ `a486aa4`).
Цель: проверить, что проект корректно запускается не только у нас, но и на
машине организаторов: чистый запуск с нуля, Docker/OPM/CHDD без локальных
костылей, честные сбои, независимость от локальных путей и старых sandbox,
устойчивость к числовым/символьным well ID и разному числу регионов.

Этот документ — сдача по двум точкам:
* 04.09 — список главных рисков + первые фиксы (сделаны);
* 06.09 — чистый end-to-end запуск и failure matrix.

## 1. Главный вывод

**Проект может быть отдан организаторам, если (а) они подключат эталонную
колоду Model Y (а не свежий экспорт tNavigator с `#if 0`), (б) смогут вытянуть
docker-образ по digest, а (в) baseline-acceptance в кейсе будет соответствовать
этой колоде.** Это три внешних условия. Код же после фиксов этого бранча:

* приводит рабочую копию к правке, которую OPM реально читает (снимает
  tNavigator `#if 0` и включает `--parsing-strictness=low`);
* не даёт симулятору упасть из-за прав пользователя контейнера;
* даёт честный типизированный сбой в любой нештатной ситуации (см. failure
  matrix в разделе 6);
* не содержит локальных путей, не требует ручной правки колоды/schedule.

## 3. Главные риски (по убыванию серьёзности)

### R1. Внешняя колода, лежащая в `MODEL_Y`, не та, что даёт frozen baseline

**Факт.** Текущий `MODEL_Y/MODEL_Y.DATA` — свежий экспорт tNavigator со
строкой `-- This file has been generated by tNavigator`, а schedule include
`DemoSpe_002_2_sch.inc` даёт digest `ac334513…`. Собранное расписание имеет
SHA `f7a374e8…`, тогда как frozen baseline ждёт `7662d104…`.
End-to-end прогон даёт **ЧДД 1082.233754 млн ₽** вместо **1030.877696**,
и контур честно останавливается:
`baseline reconciliation: NPV 1082.233754 differs from 1030.877696 by
51.356058 mln RUB (tolerance 1e-06)` → `VERDICT: BLOCKED`.

**Доказательство, что это не код.** Тот же код, что делал frozen baseline
(`efa627b` — `code_sha` из `docs/benchmark/benchmark_summary.json`, 37 коммитов
назад), с текущей колодой даёт тот же `f7a374e8…`. Значит расхождение — в
колоде, а не в коде.

**Риск на машине организатора.** Если они пришлют ту же «старую» колоду
(7662d104) — всё сойдётся. Если их колода — свежий tNavigator-экспорт — будет
та же блокировка (честная, но сабмишен не соберётся).

**Что нужно команде решить** (вне зоны runtime): зафиксировать эталонную
колоду/`MODEL_Y_ROOT`, её schedule SHA и baseline ЧДД в кейсе
`cases/model_y_validation.json` (`acceptance.baseline_npv_mln_rub`,
`acceptance.npv_tolerance_mln_rub`). Трогать acceptance без отдельного
согласования нельзя — это экономическая эталонная власть.

### R2. Колода Model Y содержит tNavigator-синтаксис `#if 0` — OPM его не читает

**Факт (воспроизведено до фикса).** В `MODEL_Y.DATA` блок
`#if 0 // tNavigator keyword … #endif`, семантически мёртвый код
тНавигатора. OPM Flow падает даже с `--parsing-strictness=low`:
`String #if 0 // tNavigator keyword not formatted as valid keyword`.

**Фикс (сделан, в этом бранче).** `prepare_workspace` снимает блоки
`#if 0 … #endif` детерминированно (`aios/opm/workspace.py` —
`_strip_tnav_dead_code`). Регресс-тест в `tests/test_opm_workspace.py`.

### R3. У `--parsing-strictness=low` нет в `main`, а он обязателен

**Факт.** Колода использует `IMPLICIT`, `GRIDFILE` — OPM без
`--parsing-strictness=low` падает (`Unsupported keywords or keyword items:
IMPLICIT`).

**Почему потеряно.** Фикс уже был на `feature/kt2-architecture-docs`
(коммит `327ac4f`), но финальная линия `main` (sync final submission) несёт
версию кейса с `extra_args: []`. Интеграционный рассинхрон.

**Фикс (сделан).** `cases/model_y_validation.json` → `extra_args:
["--parsing-strictness=low"]` (то, что было в kt2-arch), плюс тест на то, что
команда содержит флаг.

### R4. Права Docker-маунта: контейнерный `opm` (uid 1001) не может писать в `OUT/`

**Факт (воспроизведено до фикса).** Рабочая копия создаётся от uid хоста
(здесь 1000). OPM-образ запускается от внутреннего `opm` (uid 1001). Каталог
`OUT/`, созданный хостом с mode 775, не даёт записи «другим» → `flow` падает:
`Failed opening file /data/OUT/MODEL_Y.PRT for StreamLog`. На любой машине,
где uid хоста не совпадает с 1001, это даст ложный FAIL симулятора.

**Фикс (сделан).** `prepare_workspace` явно ставит `OUT/` в 0o777
(`_make_container_writable`), не завися от umask. Регресс-тест в
`tests/test_opm_workspace.py`.

### R5. Ложный красный семафор `test_external_materials_are_not_committed`

**Факт (исправлено).** Тест обходил `REPO_ROOT.rglob(...)` — всю файловую
систему дерева, включая нетрекаемые локальные `MODEL_Y/` и `CHDD_PYTHON/`.
На машине разработчика (где материалы лежат легально) тест падал, на чистом
клоне проходил. Это дезориентирует: разработчик думает, что у него красный CI.

**Фикс (сделан).** Проверка переведена на git-индекс
(`git ls-files`): ловит реальный коммит материалов, но не локальное наличие.
Позитивный контроль проверен: подложенный в индекс `MODEL_Y.SMSPEC` тест
проваливает.

### R6. Типовая муть в логике «битых» результатов — закрыта существующим кодом

Подтверждено (не требовало фикса): `OpmRunResult.is_pass` требует
`exit_code==0 AND no errors AND report_steps>0`; сводка не читается при провале;
`SimulationStatus` различает SUCCESS/CRASHED/TIMEOUT/INVALID_INPUT/
NON_CONVERGED; провал reconciliation restart-цепочки → NON_CONVERGED без
артефакта траектории (dc5d25ab уже в `main`, см. раздел 4). Failure matrix —
раздел 6.

### R7. Трение `mise trust` (см. раздел 2) — низкий риск, но надо в комплект поставки.

## 6. Failure matrix (как сбой ведёт себя, чтобы не выглядеть успехом)

| Сценарий сбоя | Наблюдаемое поведение | Статус | Где проверено |
| --- | --- | --- | --- |
| Docker недоступен (`FileNotFoundError`) | поднимается `SimulationError("docker is not available on PATH")` → типизированный CRASHED | честный FAIL | `runner.run_simulation`; цикл в `run_full_opm` не подменяет результат |
| `flow` вышел с ненулевым кодом | `exit_code != 0` → `errors` заполнены, сводка None → `SimulationResult(CRASHED)` | честный FAIL | реальный прогон (был `flow exited code 1` → `OPM: FAIL`, `BLOCKED`, сабмишен не опубликован); ЮT `test_failed_flow_becomes_crashed_not_success` |
| Таймаут | `subprocess.TimeoutExpired` → `exit_code=124`, метка TIMEOUT в логе → `SimulationStatus.TIMEOUT` | честный FAIL | ЮT `test_timeout_exit_code_maps_to_timeout` |
| Колода не читается / неизвестные ключевые слова | `Error: Unrecoverable errors while loading input` → CRASHED; сабмишен не публикуется | честный FAIL | реальный прогон (R2/R3 до фиксов) |
| `OUT/` не писабелен для контейнера | `Failed opening file /data/OUT/...PRT` → `flow` exit 1 → CRASHED (теперь исключено фиксом R4) | честный FAIL | реальный прогон до фикса |
| `#if 0` tNavigator в колоде | OPM падает даже с strictness=low (теперь исключено фиксом R2) | честный FAIL | реальный прогон до фикса |
| `.SMSPEC`/`.UNSMRY` отсутствуют | сводка не читается, `report_steps=0` → не PASS | честный FAIL | `OpmRunResult.is_pass`; `test_decode_rejects_foreign_format` |
| Отсутствует schedule-текст | `INVALID_INPUT` с причиной | честный FAIL | ЮT `test_missing_schedule_text_is_invalid_input` |
| Digest не совпал (подмена payload) | `INVALID_INPUT` с причиной | честный FAIL | ЮT `test_digest_mismatch_is_invalid_input` |
| Restart-цепочка разошлась с чистым прогоном | `NON_CONVERGED`, траектория не пишется, диагностика reconciliation в failure.details | честный FAIL | `tests/test_runtime_simulator_runtime.py` (dc5d25ab) |
| Baseline не сходится с acceptance | контур честно BLOCKED, сабмишен не публикуется, дифф в отчёте | честный FAIL | реальный прогон: `NPV 1082.23 vs 1030.877696 … BLOCKED` |
| Внешние материалы не заданы | `CaseError` с именем переменной, ничего не стирается | честный FAIL | `test_case_fails_loudly_when_external_resources_are_unset`; `test_failed_experiment_run_does_not_destroy_tracked_evidence` |
| Прогон упал в середине | частичная сводка не интерпретируется; артефакты не переписываются | честный FAIL | конструкция `run_full_opm` |

**Принцип, подтверждённый строками таблицы: ни один сбой не превращается в
успешный результат.** Сводка `SimulationResult` (physical-only, без NPV/CHDD)
появляется только при `status==SUCCESS`; в противном случае сабмишен/траектория
не публикуются, а старые артефакты не переписываются.

## 7. Числовые/символьные well ID и разное число регионов

Косвенный риск «нормально ли переживёт систему другое число регионов / другие
имена скважин» закрыт существующими тестами (все зелёные):

* `tests/test_authority_numeric_well_id.py` (26 тестов): числовые well ID
  проходят через evidence-билдеры, диагностики, специалистеские входы и
  decision-context; при этом настоящие числовые prescriptive-уставки всё ещё
  отказываются (`test_genuine_prescriptive_control_is_still_refused`);
  символьные имена продолжают приниматься;
* `tests/test_geology_regions.py` (14 тестов): чтение FIPNUM/FIPFAULT,
  run-length encoding, доминантный регион для многозонной скважины,
  детерминированность, отсутствие блокировки при отсутствии регионального
  массива. Разное число регионов не зашито в код.
* `natural_key` (`schedule/events.py`) — нативная сортировка, согласованная с
  официальным калькулятором.

Специфичного фикса под эту тему не потребовалось — риска не подтверждено.

## 8. Что нужно от команды для доведения до организаторской готовности

1. **Зафиксировать эталонную колоду** (R1): какой `MODEL_Y` ожидается на

   подготовить `docker pull` как шаг установки (R3/R4 фиксы внутри кода уже
   убрали локальную зависимость от «у кого какой uid/маунт»).

4. Принять решение по `#if 0`-колоде: наш код её снимает, но если организаторы
   будут валидировать сами, им может понадобиться аналогичная санитизация.
