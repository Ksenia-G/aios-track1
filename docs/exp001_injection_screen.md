# EXP-001 — экран перераспределения закачки

Контролируемый эксперимент, а не оптимизатор. Задача -- получить первое
измеренное улучшение ЧДД полными прогонами OPM и официального калькулятора,
не трогая ни физику модели, ни управление добывающими скважинами.

## Воздействие

Контроль -- `BASELINE_CONTINUATION`. Кандидат -- то же самое плюс один
перенос закачки внутри одной скрининговой группы:

```
для каждого шага управления в окне
    delta    = fraction × donor_baseline_target(шаг)
    donor    = donor_baseline_target(шаг) - delta
    receiver = receiver_baseline_target(шаг) + delta
```

Плановая сумма пары сохраняется на каждом шаге, а не в среднем по горизонту.
Доля переноса пропорциональна, а не задана одним абсолютным числом: иначе на
шагах, где опорная колода снижает закачку донора, перенос съедал бы весь
профиль и эксперимент перестал бы быть контролируемым.

Не меняется ничего другого: добывающие скважины, прочие нагнетательные,
ограничения по забойному давлению, статусы, физическая колода. Перевод
добывающей скважины в нагнетательные запрещён на уровне ворот Track 1.

## Скрининговые группы

Группы нагнетательных скважин заданы условием задачи. Принадлежность
добывающих скважин выведена из массива `FIPFAULT`: для каждой скважины взяты
ячейки её перфораций и определён номер региона.

| Блок | Нагнетательные | Добывающие |
|---|---|---|
| 1 | 37 | 53, 54, 55 |
| 2 | 19, 41 | 25, 30, 51, 52 |
| 3 | 4, 13, 21, 32 | 1, 6, 12, 16, 17, 20, 29, 43, 47, 49 |
| 4 | 7, 28, 42 | 9, 14, 23, 44, 45, 56 |
| 5 | 2, 15, 24, 26, 34, 36 | 3, 22, 27, 31, 33, 35, 38, 40, 48, 50 |

Вывод проверяем: он воспроизводит все пять заданных групп нагнетательных
скважин без расхождений, и ни одна скважина не пересекает границу регионов.

Блок 1 пропускается: перераспределение требует минимум двух нагнетательных
скважин.

**Это скрининговая группировка.** Она не утверждает гидродинамическую
изоляцию блоков и используется только для перебора пар и для выбора
скважин, за которыми смотреть в первую очередь.

## Перебор

Первый проход: все упорядоченные пары внутри каждой пригодной группы при
`fraction = 0.15`. Направление имеет значение: A→B и B→A -- разные сценарии.

| Блок | Пар |
|---|---|
| 2 | 2 |
| 3 | 12 |
| 4 | 6 |
| 5 | 30 |
| **Всего** | **50** |

Уточнение: пять лучших направлений по ΔЧДД прогоняются на долях
0.05, 0.10, 0.20, 0.30 -- ещё 20 сценариев. Потолок: 70 полных прогонов.

Идентификатор сценария детерминирован: `EXP001_B2_19_TO_41_F15`.

## Ворота

До каждого прогона проверяются все ворота VALIDATION-001 плюс ворота
эксперимента:

- `transfer_pair_valid` -- обе скважины существуют, обе нагнетательные,
  одна группа, донор не равен получателю, доля в (0, 1);
- `producers_untouched` -- управление добывающих скважин совпадает с опорным;
- `other_injectors_untouched` -- отличается ровно одна пара;
- `pair_injection_conserved` -- плановая сумма пары сохранена на каждом шаге;
- `transfer_magnitude_correct` -- снижение донора равно `fraction × baseline`.

Ворота считаются по разобранному расписанию кандидата, то есть по тому, что
реально увидит симулятор. Режим отказа закрытый: непройденные ворота
означают, что сценарий не запускается вовсе.

## Измерение

Каждый допущенный сценарий проходит полный прогон OPM Flow в закреплённом
образе, затем тот же 14-колоночный мост и тот же официальный калькулятор
`7.0.2-negative-row-filter`. Ни суррогатов, ни приближений, ни статических
оценок продуктивности.

Экономические допущения между прогонами не меняются, поэтому разность ЧДД
относится к воздействию, а не к настройке расчёта.

## Запуск

```bash
mise run exp001
```

Нужен запущенный Docker. Порядок жёсткий: сначала контрольный прогон, и
только если он воспроизводит принятый baseline (ЧДД 1030.8776958837277 млн
руб и SHA расписания `7662d104…`), запускается экран. Иначе -- остановка:
все выводы здесь разностные, и без сходящегося контроля разность
бессмысленна.

Параллелизм ограничен (по умолчанию 4). Каждый прогон получает свой рабочий
каталог, поэтому два процесса не могут писать в один и тот же кейс.
Экономический расчёт сериализован: официальный пакет подключается через
`sys.path` и не рассчитан на одновременный вызов.

## Выход

```
experiments/exp001/
  results.csv          -- все сценарии, отсортированы по ΔЧДД
  summary.json         -- сводка прогона экрана
  baseline.json        -- контрольный прогон
  comparisons/         -- разности физики каждого сценария с контролем
  runtime/<scenario>/  -- расписание, результат, метрики, хвост лога
```

Артефакты эксперимента лежат отдельно от `output/` и не являются пакетом
сабмишена. Каждый результат связан со своим прогоном: идентификатор
сценария, SHA расписания, статус OPM и результат ЧДД лежат в одном файле и
переписываются целиком, поэтому устаревшее число не переживает неудачный
повтор.

Тяжёлые бинарники прогона удаляются после снятия метрик, кроме контрольного
прогона: 70 полных наборов вывода OPM -- это единицы гигабайт без пользы для
последующего разбора.

## Как читать результат

ЧДД -- единственное основание для ранжирования. Физические разности нужны,
чтобы понять, откуда взялся эффект, но сами по себе они его не доказывают.

Полученный эффект классифицируется как `OBSERVED_SIMULATION_EFFECT`. Это
поведение конкретной модели при конкретном воздействии, а не доказанный
пластовый механизм и не доказанная связность скважин. Один эксперимент не
даёт права на такие утверждения.

Происхождение ЧДД остаётся `NOT_OFFICIAL_PENDING_TNAV_REFERENCE` -- по той
же причине, что и в VALIDATION-001: массовый мост между объёмами OPM и
массами калькулятора не сверен с эталонной выгрузкой tNavigator. Разности
ЧДД между сценариями от этого страдают меньше, чем абсолютные значения,
поскольку мост одинаков во всех прогонах, но снятой пометка от этого не
становится.
