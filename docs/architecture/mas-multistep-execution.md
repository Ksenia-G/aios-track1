# Многошаговое исполнение MAS: receding horizon на композитном расписании

Документ фиксирует семантику многошагового замкнутого контура MAS v1.1.
До него `--decision-steps N > 1` был неисполним: когнитивный слой продвигался
(StateCard, `previous_committed`), а физический оставался привязан к исходному
состоянию окна, и два определения HOLD расходились между оркестратором и
компилятором.

## Эпохи решения

Решение принимается в `N` эпохах, детерминированно разложенных по окну
управления и посаженных на существующую сетку отчётных шагов колоды.

    T_i = grid[round(i * (n - 1) / N)],  i = 0 .. N-1

где `grid` -- канонические даты опорного расписания (они же -- единственные
легальные `effective_date`, см. `compile_candidate_schedule`), `n = len(grid)`.

Для Model Y (`cases/model_y_validation.json`, 24 месячных шага) и `N = 3`:

| эпоха | индекс | дата |
|---|---:|---|
| `T0` | 0 | 2014-01-01 |
| `T1` | 8 | 2014-09-01 |
| `T2` | 15 | 2015-04-01 |
| `H`  | 23 | 2015-12-01 |

`H` -- фиксированный конец горизонта, а НЕ дополнительная эпоха решения.
Второй регулятор частоты (шаг каденции) намеренно не вводится: у бенчмарка
остаётся ровно одна ручка `--decision-steps`, и рамка сравнения (`PhysicalFrame`)
не меняет форму.

## Композитное расписание

Кандидат в эпохе `T_i` компилируется в ОДНО полное расписание окна:

    неизменяемая закоммиченная история на [T0, T_i)
    + управления кандидата на [T_i, H]

и исполняется как одна физическая траектория `T0 -> H`.

Отсюда следует главное свойство: физическое состояние в `T_i` внутри любого
прогноза кандидата -- это состояние, порождённое управлениями, которые
действительно были закоммичены до `T_i`. Отдельный механизм restart для этого
не нужен.

Закоммиченный префикс -- неизменяемая история. Кандидат в `T_i` не имеет права
менять ни один интервал управления до `T_i`; ему принадлежит только `[T_i, H]`.

## HOLD и DETERMINISTIC_BASELINE

Это НЕ синонимы, и на второй эпохе они расходятся:

* `HOLD(T_i)` -- продолжить ровно те управления, которые закоммичены на
  `T_{i-1}`. Проверяется инвариантом T6 (`require_hold_carry_forward`) против
  управлений, действующих в `T_i`, а не против исходного baseline окна.
* `DETERMINISTIC_BASELINE` -- детерминированная опорная политика, применяемая
  от текущей эпохи; её численный источник -- исходный baseline, но исполняется
  она поверх той же неизменяемой закоммиченной истории.

Требование замороженного контракта («в наборе кандидатов обязан быть
DETERMINISTIC_BASELINE») сохраняется без ослабления.

## Продвижение когнитивного состояния

Композитное расписание закрывает физику прогнозов, но не заменяет привязку
когнитивного состояния. Для `T_i > T0`:

    выбранный кандидат в T_{i-1}
    -> его физический прогон
    -> отчётный шаг на дату T_i
    -> StateCard(T_i)
    -> следующее когнитивное решение

`StateCard(T_i)` извлекается из сводки ИМЕННО выбранного кандидата на отчётном
шаге даты `T_i` (`StateExtractor.extract(step=...)`), а не из невыбранного
кандидата, не из перегенерированного baseline и не из чисто когнитивного
перехода. Существующие проверки идентичности прогона
(`_require_execution_identity`, `VerifiedRealizedState`) остаются в силе.

## Экономика: прогноз против реализованного

Прогнозы кандидатов по построению перекрываются (`T0->H`, `T1->H`, `T2->H`) --
это и есть receding horizon. Складывать их ЧДД нельзя: перекрывающиеся периоды
были бы посчитаны дважды.

Разделение:

* ЧДД кандидата на шаге -- свидетельство ДЛЯ ОТБОРА (`EconomicSelector`), и
  только оно;
* авторитетная экономика траектории считается ОДИН раз по реализованной
  композитной политике на `T0..H`.

Ключевое тождество: кандидат, выбранный в последней эпохе, уже содержит
закоммиченную историю всех предыдущих эпох плюс собственный хвост, то есть
ЯВЛЯЕТСЯ полной реализованной композитной политикой `T0 -> H`. Поэтому его
обычный полный прогон OPM + ЧДД и есть авторитетный итоговый результат:
дополнительного финального прогона не требуется, а суммирования прогнозов не
происходит нигде.

## Что осталось прежним

Границы авторитета не меняются: numerical control по-прежнему появляется
только в MagnitudeResolver, Arbiter остаётся структурным, NO SETPOINTS CROSS и
привязки прогон -> Guardian -> ЧДД сохранены. Механизм
`run_restart_chain`/`RestartSpec`/`ExecutionMode.RESTART` не трогается: он
остаётся самосверкой одной и той же политики, а не переносом состояния между
разными политиками.
