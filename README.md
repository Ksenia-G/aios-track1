# AIOS Track 1

Решение задачи «Мультиагентная система оптимального управления на основе
гидродинамической модели».

## Что делает система

Замкнутый контур управления заводнением: из кейса, истории и ограничений
строится план управления скважинами, он превращается в файл расписания
колоды, считается полным прогоном гидродинамического симулятора, из
траектории собирается экономический вход, и официальный калькулятор даёт
ЧДД. Каждый шаг проверяем и воспроизводим.

```
КЕЙС / ИСТОРИЯ / ОГРАНИЧЕНИЯ
  ↓
ПЛАН УПРАВЛЕНИЯ
  ↓
wells_schedule.inc
  ↓
OPM Flow
  ↓
ТРАЕКТОРИЯ СОСТОЯНИЯ
  ↓
РАСЧЁТ ЧДД
  ↓
ПРОВЕРКА ОГРАНИЧЕНИЙ
  ↓
ПРОВЕРЕННЫЙ РЕЗУЛЬТАТ
```

Ограничения проверяются до симулятора: непроходной план не тратит счёт.
Пакет сабмишена публикуется транзакционно — заявка на результат появляется
только после прохождения всех ворот.

## Текущий статус

Контур проверки: **ПРОЙДЕН**

## Проверенный результат

| | млн ₽ |
|---|---|
| Базовый сценарий | 1030.877696 |
| Лучший из полностью просчитанных сценариев | 1190.593386 |
| Прирост | +159.715690 (+15.493 %) |

Происхождение результата: **неофициальное — ожидается сверка с tNavigator**
(`NOT_OFFICIAL_PENDING_TNAV_REFERENCE`)

Водный баланс: **точное правило требует подтверждения организатора**
(`ORGANIZER_RULE_UNRESOLVED`)

Ограничение по давлению для приведённого выше расчёта: официальный порог не
был подключён к проверке ограничений на момент этого прогона (снимок
KT1-демонстрации это фиксирует и не пересчитывается задним числом). С тех
пор организаторские значения подтверждены и используются в MAS-контуре
(`producer_bhp_min = 50 bar`, `injector_bhp_max = 300 bar`,
`producer WLPR <= 500 m³/day`) -- см. `docs/team/organizer-constraints.md`.

Это лучший из просчитанных сценариев, а не глобальный оптимум и не
подтверждённый организатором результат. Каждое число получено полными
расчётами OPM Flow и официального пакета расчёта ЧДД; ни одно не
экстраполировано.

## Внешние данные

Колода Model Y и официальный пакет расчёта ЧДД **намеренно не входят в
репозиторий**: это материалы организаторов, и их место — вне системы
контроля версий. Репозиторий содержит код, конфигурацию и агрегированные
свидетельства экспериментов.

Настройка не требует правки исходного кода:

```bash
cp .env.example .env
# и указать свои пути:
#   MODEL_Y_ROOT=/path/to/model-y      # каталог с MODEL_Y.DATA
#   CHDD_ROOT=/path/to/chdd-python     # каталог с chdd_model.py
```

Без этих переменных работают проверки и демонстрация; живые прогоны
останавливаются с явным сообщением о том, какая переменная не задана.

Живые команды (нужны Docker и внешние материалы):

```bash
mise run validation-demo   # сквозной прогон и пакет сабмишена
mise run exp001            # экран перераспределения закачки
mise run exp003            # конверт робастности
```

## Hybrid MAS v1.1 -- team foundation

EXP001-004 -- завершённая экспериментальная линия (historical lineage), не
переписывается задним числом. Поверх неё зафиксирован typed contract layer
для будущей мультиагентной системы: `docs/architecture/mas-v1.1-contracts.md`,
`docs/architecture/mas-v1.1-diagnostics.md`. Специалисты, Arbiter,
MagnitudeResolver, Orchestrator и PredictiveSafetyScreen пока не
реализованы -- это frozen contracts + deterministic invariant guards, а не
законченная MAS.

Точка входа для новых участников команды: [docs/team/README.md](docs/team/README.md).

## Воспроизводимость

Демонстрация читает сохранённые материалы экспериментов и не пересчитывает
их. Живые расчёты воспроизводятся отдельными командами и начинаются со
сверки базового сценария.

## Что уже доказано

- контрольный расчёт воспроизводит базовый сценарий точно, вместе с SHA
  файла расписания, и каждый эксперимент начинается с этой сверки;
- построенный экономический вход байт в байт совпадает с эталонным;
- бинарные результаты симулятора совпадают с опорным расчётом.

## Что ещё требует подтверждения

- **эквивалентность tNavigator.** Массовый мост между объёмами OPM и
  массами калькулятора не сверен с эталонной выгрузкой tNavigator.
  Плотности взяты из колоды, но равенство величин не подтверждено —
  отсюда пометка `NOT_OFFICIAL_PENDING_TNAV_REFERENCE`.
- **трактовка водного баланса.** Водный учёт поверхностный, по модели. Это
  не VRR и не замещение отбора в пластовых условиях; официальное правило не
  определено — отсюда `ORGANIZER_RULE_UNRESOLVED`.
- **порог по давлению в приведённом выше расчёте.** На момент этого прогона
  официальный порог не был подключён к проверке ограничений, поэтому там
  пластовое давление осталось метрикой риска, а не ограничением. С тех пор
  организаторские значения подтверждены (см. `docs/team/organizer-constraints.md`)
  и используются в MAS-контуре (`aios.state`, `aios.agents.constraint_guardian`).

Эти пометки — часть результата, а не оговорки: по ним видно, что именно
проверено, а что ещё нет.
